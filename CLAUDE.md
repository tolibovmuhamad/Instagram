## Текущее состояние репозитория

Репозиторий пока **содержит только спецификацию**. Единственный содержательный файл — `TZ_Instagram_Frontend (1).md` — это техническое задание (ТЗ, на русском) на **фронтенд** клона Instagram. ## Кратко о проекте

Нужно построить адаптивный веб-клиент, повторяющий UX Instagram (лента, сторис, профиль, лайки/комментарии, подписки, личные сообщения), поверх **уже готового** бэкенда. Разрабатывается **только фронтенд**.

- **Формат:** учебный/командный pet-project с возможностью деплоя (Vercel/Netlify).
- **Цель:** функциональный адаптивный клиент, максимально близкий к оригинальному Instagram по виду и UX, полностью покрывающий доступные возможности backend API.
- **Дизайн-референс:** веб-версия оригинального Instagram — используется только как UX-эталон и источник вдохновения (общая раскладка и паттерны), **без официального логотипа и брендинга** Meta/Instagram.

## Бэкенд (НЕ разрабатываем, только интегрируемся)

- ASP.NET Core 8 Web API, PostgreSQL + EF Core, JWT Bearer, Clean Architecture.
- Swagger: https://instagram-backend-ea2y.onrender.com/swagger/index.html
- **Realtime почти везде отсутствует.** Чат, уведомления, счётчики эфира — через REST + периодический опрос (polling — React Query `refetchInterval`). Онлайн-статус — тоже опрос (`/Presence/get-status`). **Единственное исключение — SignalR-хаб `LiveHub` (`/liveHub`)**: по нему бэкенд пушит событие `GuestApproved` с publisher-токеном одобренному гостю эфира (иначе право публиковать не получить, см. раздел «Эфиры»). Больше сокетов нигде нет — не заводить их для чата/уведомлений.
- CORS разрешает любой origin (`*`) — dev-сервер и деплой на Vercel работают без согласования.
- Хостится на Render (free tier): сервис засыпает после ~15 мин простоя, первый запрос после сна может ждать до минуты.

> ⚠️ **Смена бэкенда (июль 2026).** Проект переехал со старого `instagram-api.softclub.tj` на новый. Старый упоминается только в `TZ_Instagram_Frontend (1).md` (исторический документ) — в коде его быть не должно. Новый API — надмножество старого (110 эндпоинтов против 57), но **DTO переименованы**, см. таблицу ниже.

### Авторизация: пара access/refresh (июль 2026)

`/Account/login` и `/Account/register` **больше не отдают строку JWT** — теперь это
`{accessToken, refreshToken, expiresIn, sessionId}` (схемы в Swagger нет, форма выяснена
запросом). `expiresIn` = **900 секунд**, поэтому обновление по `POST /Account/refresh-token`
обязательно, иначе сессия умирает через 15 минут. В JWT появился claim `sessionId`.

> ⚠️ **refreshToken одноразовый и ротируется.** Повторное использование бэкенд считает
> атакой: отвечает `401` «Обнаружено повторное использование токена. Все сессии завершены.»
> и **действительно завершает все сессии пользователя** (проверено). Приложение опрашивает
> сервер поллингом, так что по истечении токена 401 прилетает пачкой — обновление обязано
> быть строго однопоточным. Реализовано в `lib/api/client.ts`: single-flight-очередь
> **на каждый аккаунт** (`refreshPromises: Map<userId, Promise>`) + Web Locks с именем лока
> по userId (между вкладками) + перечитывание localStorage по `storage`-событию в
> `store/auth.ts`. Инвариант закреплён тестом `lib/api/__tests__/refresh.test.ts` — не ломать.

### Мультиаккаунт (клиентская фича, июль 2026)

Приложение держит **несколько аккаунтов** сразу и мгновенно переключается между ними без
повторного логина. Бэкенд про это не знает — `/Account/login` можно звать сколько угодно раз,
каждый выдаёт свою пару токенов; мультиаккаунт целиком клиентский.

- Стор `store/auth.ts` хранит `accounts: Account[]` + `activeUserId` (persist в том же ключе
  `auth-storage`, версия схемы **4**, есть миграция v3→v4: одиночная сессия сворачивается в
  массив из одного аккаунта — старые пользователи не разлогиниваются). Поля `accessToken`/
  `refreshToken`/`sessionId`/`user` остались как **зеркало активного аккаунта** — ради
  обратной совместимости с ~20 существующими селекторами; пересобираются в каждом экшене.
- HTTP-клиент подставляет токен **активного** аккаунта и штампует запрос `_accountUserId`.
  При 401 обновляется токен именно **этого** аккаунта (он мог быть фоновым — активный успел
  смениться, пока запрос летел). Провал refresh → аккаунт удаляется из списка.
- **Гигиена при переключении** (`features/auth/useAccounts.ts`): `cancelQueries()` +
  `queryClient.clear()`, иначе данные прошлого аккаунта «протекут» на экран. Плюс единый
  страж в `app/providers.tsx` — подписка на смену `activeUserId` чистит кэш при **любом**
  источнике смены (в т.ч. авто-удалении активного из axios-интерцептора, где queryClient
  недоступен). SignalR-хаб `LiveHub` переподключается по `authEpoch` (см. `useLiveHub.ts`).
- UI-переключатель: `components/nav/AccountSwitcherDialog.tsx` (из «Ещё» в сайдбаре и из
  шестерёнки своего профиля — чтобы фича была и на мобильном). Лимит **5** аккаунтов.
  «Добавить аккаунт» = `/login?add=1` (тот же логин, список не затирается).
- Инвариант закреплён тестами `store/__tests__/auth.test.ts` (add/switch/remove/logoutAll,
  dedup, лимит) и `lib/api/__tests__/refresh.test.ts` (per-account single-flight) — не ломать.

### Эфиры (`/Live`) — LiveKit, появился 17.07.2026

Контроллер `/Live` (26 эндпоинтов) — прямые эфиры поверх **LiveKit Cloud**. Бэкенд хранит
состояние эфира и раздаёт токены, **видео идёт мимо нашего API** через
`wss://instagram-qiexploa.livekit.cloud`. Клиент — `livekit-client`, весь WebRTC заперт в
`features/live/useLiveRoom.ts`.

- `/Live/start` (хосту) и `/Live/join` (зрителю) возвращают `{streamId, roomName, token, serverUrl}`.
  `token` — это **JWT для LiveKit, не для нашего API**; `serverUrl` брать только из ответа,
  не хардкодить. Права зашиты в токен: у хоста `canPublish: true`, у зрителя `false`.
- **Токен публикации выдаётся один раз.** Повторно его не получить: `join` хосту вернёт
  токен зрителя, без права публиковать. Поэтому `StartLiveView` кладёт доступ в
  `sessionStorage`, а `LiveRoomView` читает его лениво при инициализации состояния.
  Перезагрузка страницы хоста = потеря камеры (показываем это явно).
- `/Live/webhook` вызывает **LiveKit в наш бэкенд** (сверяет подпись по сырому телу) —
  фронтенд к нему не обращается, в `features/live/api.ts` его намеренно нет.
- Realtime тут только для видео: комментарии, счётчики и заявки в гости — **опрос**
  (комментарии 3 с, эфир 5 с, список активных 30 с).

**Грабли (всё выяснено запросами, схем ответа в Swagger нет ни у одного эндпоинта):**

| Что | Как на самом деле |
|---|---|
| Ключ эфира | `streamId`, **не** `id` |
| Ключ заявки в гости | `requestId`, **не** `id`; `approve/decline` ждут именно его |
| `audience` | на вход **число** (0=все, 1=близкие друзья), с сервера **строка** (`All`/`CloseFriends`) |
| `update-title` | возвращает фразу «Заголовок эфира обновлён.», а не boolean |
| `guests` в DTO | массив в `get-stream-by-id`, но `null` в списке `get-active` |
| Пагинация | есть у `get-active`, `get-comments`, `get-viewers`, `get-my-streams`; `get-guest-requests` и `get-active-guests` — голые массивы |
| `get-active` | только эфиры тех, **на кого подписан** — без подписки список пуст (не баг) |
| Бан | `join` забаненного → 403 «Вы забанены в этом эфире.» |
| Второй `start` | 400 «У вас уже идёт активный эфир.» — активный эфир только ОДИН на пользователя |

> ⚠️ **Эфир не гаснет сам, если бросить вкладку.** Закрыл страницу — эфир остался `Live`
> навсегда, и следующий `start` отвечает 400. Автозавершение по вебхуку LiveKit
> (`room_finished`) тут не спасает: если хост так и не подключился к комнате (запретил
> камеру, ушёл со страницы), комнаты в LiveKit не было — значит и завершать нечего.
> Поэтому `/live/start` сам находит свой незавершённый эфир (`useMyActiveStream`) и
> предлагает вернуться или завершить, а кнопка старта заблокирована. **Не убирать** —
> без этого пользователь упирается в необъяснимый 400 (на этом уже погорели 17.07.2026).
>
> Там же: **не подменять текст ошибки своим**. Перехватчик axios уже показывает фразу от
> сервера, а общее «Не удалось начать эфир» её прятало.

> ✅ **Эфиры: realtime через SignalR-хаб `LiveHub` (обновлено 17.07.2026).** Единственные
> сокеты в проекте. Путь `/liveHub` (под `[Authorize]`, токен через `accessTokenFactory`),
> метод входа в группу эфира — `JoinStream(streamId)`. Всё выяснено запросами к хабу, в
> Swagger хабов нет. События (payload в camelCase):
> - **`GuestApproved`** → гостю: publisher-токен после одобрения. Payload = `JoinLiveResultDto`
>   (`streamId`/`roomName`/`token`/`serverUrl`), внутри токена `canPublish:true`. **Достать
>   его можно ТОЛЬКО этим событием**: REST `/Live/join` даже одобренному гостю отдаёт
>   `canPublish:false` (проверено сквозным прогоном 17.07.2026). Приходит адресно, без `JoinStream`.
> - **`GuestRequestReceived`** → хосту: новая заявка в гости сразу, payload = `LiveGuestRequest`
>   (`requestId`/`user`/`requestedAt`/`status`). Идёт через группу — нужен `JoinStream`.
> - Ещё хаб шлёт `ViewerJoined`, `viewercount`, `StreamEnded` — пока не используем (остаётся опрос).
>
> Фронт: `features/live/useLiveHub.ts` — одно соединение на экран, раздаёт события по роли.
> `LiveRoomView` по `GuestApproved` кладёт токен в `guestAccess` и переключает `useLiveRoom`
> в `publish: true` (переподключение к LiveKit + камера + самопросмотр гостя), а по
> `GuestRequestReceived` (у хоста) инвалидирует `liveKeys.guestRequests`. Опрос заявок (5 c)
> оставлен как страховка на случай пропущенного пуша.
>
> ⚠️ **`save-to-story` не работает:** записи эфиров не ведутся (`recordingUrl` всегда
> `null`), сервер отвечает 400 «Нет записи эфира для сохранения в сторис.». Кнопка в UI
> показывается только при наличии `recordingUrl` — то есть пока никогда.

### Модули без схем в Swagger (значения выяснены запросами к API)

Часть модулей описана в Swagger только путями — тела ответов пустые (`content?: never`),
поэтому сгенерированные типы тут не помогают, а TypeScript ошибку не поймает:

- **`/Chat/create-chat`** возвращает **чат целиком** (`{id, userId, userName, …}`), а не id.
  На этом уже погорели: объект уходил в URL, `/messages/[object Object]` → 404.
- **`/Notification/get-notifications`**: `type` 0=лайк, 1=подписка, 2=комментарий;
  `entityType` 0=пост, 3=пользователь; `entityId` — id поста, у подписки `null`.
  Зафиксировано в `features/notifications/types.ts`. Отметки прочтения — **`PUT`**.
- **`/Explore/get-feed`** (персональные рекомендации) и **`/Explore/get-popular`**
  (cold start) отдают обычную пагинированную ленту постов. **Различать их контентом
  бессмысленно:** проверено 16.07.2026 — оба возвращают одни и те же посты в одном и том же
  порядке, персонализации на бэкенде фактически нет (вопрос ей задан, см. ROADMAP).
- **`/Session/get-active-sessions`** — плоский массив (без пагинации) строк вида
  `{id, deviceName, deviceType, browser, os, ipAddress, location, createdAt, lastActivityAt, isCurrent}`.
  `deviceType` — не enum, а строка; реальных значений три: `Web`, `Mobile`, `Unknown`
  (планшет тоже `Mobile`). `deviceName` приходит уже по-русски («Chrome на Windows»).
  `os`/`location` часто `null`. Отзыв: `DELETE /Session/revoke-session?sessionId=…`
  (на неизвестный id — 400 «Некорректный Id сессии.») и `DELETE /Session/revoke-all-others`.
  Зафиксировано в `features/sessions/types.ts`.

### Картинки: диск на Render эфемерный

Файлы раздаются с `${API_URL}/images/{filename}` (путь верный), но при перезапуске сервиса
загруженное **исчезает**, а записи в БД остаются — старые посты отдают 404 на картинку.
Это не баг фронтенда; UI просто показывает заглушку вместо битого изображения.

**Про 401 на `/images/*` — не обманываться.** Раздача **открыта**, авторизацией её не
закрывали (проверено 16.07.2026: свежезагруженный файл отдаётся с 200 без токена). 401
приходит только на **отсутствующий** файл: запрос проваливается мимо статики в
авторизованный роут, и тот отвечает 401 без токена и 404 с токеном. То есть 401 — это тот
же «файла нет», а не отдельная проблема; чинить нечего, пока файлы стираются.

Настоящая причина одна — эфемерный диск (см. выше). Лечится только на бэкенде: постоянный
сторедж (S3/Cloudinary) или диск Render. Вопрос открыт к backend-команде.

### Комментарии поста — дыра закрыта (эндпоинт с 15.07.2026)

`GET /Post/get-comments?postId=&pageNumber=&pageSize=` **работает** (перепроверено запросом
17.07.2026). Этот раздел долго врал, что эндпоинта нет: он появился ещё 15.07, список ожил
сам, но заглушка «Комментарии временно недоступны» и обработка 404 жили в коде до 17.07 —
теперь убраны.

Схемы ответа в Swagger, как обычно, нет; форма выяснена запросом (проверено 17.07.2026):
обычный пагинированный конверт (`data`, `errors`, `statusCode`, `pageNumber`, `pageSize`,
`totalPages`, `totalRecords`), DTO — ровно наш `PostComment` (`id`, `postId`, `comment`,
`createdAt`, `userId`, `userName`, `userImage`, `isVerified`, `parentCommentId`,
`repliesCount`, `likesCount`, `isLiked`, `mentionedUsers`).

- Отдаёт **только корневые** комментарии; ответы по-прежнему через `get-comment-replies`.
- Поэтому `commentCount` поста **больше** количества записей в `get-comments`: счётчик
  считает и ответы (у поста id=5 — `commentCount: 6` против `totalRecords: 5`).
- В e2e селектор удаления поста теперь обязан быть `getByRole("menuitem", …)`: у каждого
  своего комментария в списке есть своя кнопка «Удалить», и `getByText("Удалить")` находит
  несколько элементов. На этом уже падал тест, когда список ожил.

### `Jest worker encountered N child process exceptions` — перезапустить dev-сервер

Ошибка в оверлее Next вида «Jest worker encountered 2 child process exceptions, exceeding
retry limit» (в логе рядом — `write EPIPE` и `Failed to generate static paths for /…/[id]`)
**не связана ни с Jest, ни с кодом страницы**. Так проявляется выдохшийся `next dev`:
процесс, проживший часы, раздувается (ловили на 1.7 ГБ) и перестаёт спавнить воркеры,
которыми Next вычисляет статические пути. Отсюда характерная примета — **500 отдают только
динамические маршруты** (`/profile/[id]`, `/post/[id]`), а статические (`/`, `/explore`)
работают. Проверено 16.07.2026: пустая страница `[id]` без единого импорта тоже падала,
после перезапуска сервера всё стало 200. Лечение — перезапустить `npm run dev`; искать
причину в своём коде не нужно. Лог: `.next/dev/logs/next-development.log`.

**Вариант того же сбоя — 404 вместо 500, лечится сносом `.next`.** 17.07.2026 динамические
маршруты (`/profile/[id]`, `/post/[id]`, `/messages/[chatId]`) дружно отдавали **404**, а
статические — 200; в логе никаких Jest-воркеров, только 401 на картинки (это про другое,
см. выше). Примета — **побитый сгенерированный `.next/dev/types/routes.d.ts`**: кусок файла
записан поверх самого себя (обрывок `oute extends LayoutRoutes> = {`), из-за чего
`npx tsc --noEmit` сыплет `TS1435`/`TS1128` **в самом `.next`, а не в `src/`** — верный
признак, что дело в кэше. Простого перезапуска мало: нужно снести `.next` целиком
(он в `.gitignore`, генерируется заново) и поднять `npm run dev`. Диагностика в один шаг —
сравнить коды статики и динамики:
`for p in / /explore /profile/test-id-123 /post/abc; do curl -s -o /dev/null -w "%{http_code} $p\n" localhost:3000$p; done`.
Если статика 200, а динамика нет — это кэш, а не код.

## Конвенции API бэкенда (критично для интеграции)

Каждый ответ обёрнут в стандартный конверт — **разворачивать `data` в axios-слое**, показывать `errors[]` через тост:

```json
{ "data": {}, "errors": [], "statusCode": 200 }
```

Пагинированные списки дополнительно содержат `pageNumber`, `pageSize`, `totalPage`, `totalRecord` — **infinite scroll строить по ним**, а не по клиентскому подсчёту.

- Создание поста и сторис — **multipart/form-data** (изображения + текст + категории).
- Авторизация — под `/Account` (`register`, `login` → JWT). Внимание к нестандартным глаголам: бэкенд использует **`DELETE`** для ForgotPassword/ResetPassword и **`PUT`** для ChangePassword — повторять эти глаголы точно.

## Эндпоинты, которые могут быть отключены

Часть модулей бэкенда закомментирована на сервере. **Проверяй доступность перед подключением**; 404 здесь — не обязательно баг фронтенда:

- **`/FollowingRelationShip`** (подписаться/отписаться, списки подписчиков) — на момент ТЗ был закомментирован.
- Модуль **`UserSetting`** — полностью закомментирован; возможно, вне MVP.

## Функциональные модули и эндпоинты

### Авторизация и аккаунт (`/Account`)
`POST register` · `POST login` → JWT · `DELETE ForgotPassword` · `DELETE ResetPassword` · `PUT ChangePassword`.
Экраны: вход, регистрация, восстановление пароля, смена пароля в настройках.

### Профиль (`/UserProfile`, `/User`)
`GET get-my-profile` · `GET get-user-profile-by-id` · `GET get-is-follow-user-profile-by-id` · `PUT update-user-profile` · `PUT/DELETE …-user-image-profile` · `GET get-post-favorites` · `GET /User/get-users` · история поиска (`add/get/delete-search-history(ies)`, `…-user-search-history(ies)`).
Экраны: профиль (свой/чужой), редактирование, поиск пользователей с историей, сохранённые посты.

### Посты (`/Post`)
`GET get-posts` · `GET get-following-post` · `GET get-reels` · `GET get-post-by-id` · `GET get-my-posts` · `POST add-post` (multipart) · `DELETE delete-post` · `POST like-post` · `POST view-post` · `POST add-comment` · `DELETE delete-comment` · `POST add-post-favorite`.
Экраны: главная лента, страница поста с комментариями, создание поста (кроп/превью), Reels, сетка постов в профиле.

### Сторис (`/Story`)
`GET get-stories` · `GET get-user-stories/{userId}` · `GET get-my-stories` · `GET GetStoryById` · `POST AddStories` · `DELETE DeleteStory` · `POST LikeStory` · `POST add-story-view`.
Экраны: лента аватарок-сторис над лентой, полноэкранный вьюер с прогресс-баром, создание сторис.

### Подписки (`/FollowingRelationShip`) — см. предупреждение выше
`GET get-subscribers` · `GET get-subscriptions` · `POST add-following-relation-ship` · `DELETE delete-following-relation-ship`.
Экраны: списки подписчиков/подписок, кнопка «Подписаться/Отписаться» в профиле и под постом.

### Личные сообщения (`/Chat`)
`GET get-chats` · `GET get-chat-by-id` · `POST create-chat` · `PUT send-message` (текст + файл) · `DELETE delete-message` · `DELETE delete-chat`.
Экраны: список диалогов, окно переписки (обновление — через polling).

### Геолокация (`/Location`)
CRUD: `get-Locations`, `get-Location-by-id`, `add-Location`, `update-Location`, `delete-Location`.
Использование: выбор города в профиле; привязка к посту — уточнить у backend-команды.

## Нефункциональные требования

- **Адаптивность обязательна:** корректно от 360px до 1920px+; три раскладки навигации (desktop-сайдбар / tablet / mobile нижний таб-бар), как в оригинале.
- **Производительность:** ленивая загрузка (`next/image`), виртуализация длинных списков при необходимости, infinite scroll вместо кнопочной пагинации.
- **Безопасность:** JWT не хранить в localStorage «как есть» без осознанного решения команды (обсудить httpOnly cookie vs память + refresh); экранировать пользовательский контент (XSS в комментариях/подписях).
- **Обработка ошибок:** единый обработчик (interceptor axios + `errors[]`), понятные сообщения через toast; у каждого экрана состояния loading/error/empty.
- **A11y:** alt у изображений, фокус-стили, клавиатурная навигация в модалках.
- **Тема:** рекомендуется светлая/тёмная (Tailwind + shadcn упрощают).

## Ориентиры по UI/UX (из оригинального Instagram)

- **Раскладка:** слева сайдбар навигации (Главная, Поиск, Reels, Сообщения, Уведомления, Создать, Профиль) на десктопе; нижний таб-бар на мобильном.
- **Лента:** центральная колонка постов + панель сторис сверху + правый блок «рекомендации/подписки» на широких экранах.
- **Пост:** шапка (аватар, ник, локация, «…»), медиа-карусель, панель действий (лайк, комментарий, поделиться, сохранить), подпись, превью комментариев, дата.
- **Сторис:** полноэкранный просмотр, прогресс-бар сегментов, переход клик/свайп влево-вправо, реакция и просмотры (для автора).
- **Профиль:** аватар, статистика (посты/подписчики/подписки), «Редактировать профиль»/«Подписаться», вкладки (посты сеткой, сохранённое, отмеченные), bio.
- **Создание поста:** загрузка/кроп (1:1, 4:5, 16:9), подпись, категория/локация.
- **Модалки:** подписчики/подписки, лайкнувшие, комментарии (на десктопе — модалка, на мобильном — отдельный экран).
- **«Поиск» и «Интересное» — разные вещи, не сваливать в одно.** На десктопе «Поиск» это
  **выдвижная панель** (`components/nav/SearchPanel.tsx`): поле и история, **без сетки**.
  Сетка есть только у «Интересного» (`/explore`). На мобильном наоборот — вкладка поиска
  *и есть* Explore: страница `/search` с сеткой «Популярное» под строкой поиска, поэтому
  `/explore` помечен `desktopOnly`. Общая часть обоих — `components/search/SearchBox.tsx`.
  Если снова добавить сетку в десктопный поиск, вернётся дубль, который мы уже убирали.

## Планируемая структура проекта (цель после скаффолдинга)

```
src/
  app/                    роуты Next.js (App Router)
    (auth)/               login, register, forgot-password
    (main)/               feed, explore, reels, profile/[id], post/[id], messages
  components/ui/          примитивы shadcn
  components/{post,story,chat,profile}/
  features/               доменные модули (posts, stories, users, chat, auth)
  store/                  zustand-сторы (auth, ui)
  lib/api/                axios-инстанс, interceptors, сгенерированные из Swagger типы
  lib/hooks/              обёртки-хуки React Query
  lib/utils/
```

**Архитектурный замысел:** доменная логика — в `features/`; переиспользуемые презентационные части — в `components/ui`; весь доступ к серверу идёт через axios-инстанс в `lib/api` (разворачивание конверта + JWT + обработчик ошибок в одном месте) и потребляется исключительно через хуки React Query в `lib/hooks`.
