# Промпт: Мультиаккаунт (переключение между аккаунтами) — React / Next.js

> Это задача **для фронтенда**. Бэкенд менять не нужно — он уже поддерживает несколько независимых сессий (`/Account/login` можно вызывать сколько угодно раз, каждый вызов выдаёт свою пару токенов).
> Мультиаккаунт — целиком клиентская фича: приложение хранит несколько пар токенов и подставляет нужную в заголовок `Authorization`.

## Текущее состояние (проблема)

Сейчас хранится **один** токен — новый вход затирает предыдущий, поэтому для смены аккаунта нужно выйти и войти заново.

```
Логин  → сохранили токен (перезаписав старый)
Выход  → стёрли токен
```

## Целевое поведение

```
Логин         → добавили аккаунт в список
Переключение  → взяли токен другого аккаунта из списка
Выход         → убрали один аккаунт из списка
```

- Пользователь может добавить несколько аккаунтов и переключаться между ними **мгновенно**, без ввода пароля.
- После переключения все данные (лента, профиль, чаты, уведомления) — уже нового аккаунта.
- Список аккаунтов сохраняется между перезагрузками страницы.

## Контракт бэкенда

| Эндпоинт | Описание |
|---|---|
| `POST /Account/login` | → `{ accessToken, refreshToken, expiresIn, sessionId }` (access ~15 мин, refresh ~30 дней) |
| `POST /Account/refresh-token` | body `{ refreshToken }`, без авторизации → новая пара токенов. **Ротация**: старый refresh становится невалидным |
| `POST /Account/logout` | отзывает текущую сессию |
| `GET /UserProfile/get-my-profile` | данные текущего юзера (по токену) |

- Все ответы обёрнуты в `Response<T> { data, errors, statusCode }`
- Авторизация: заголовок `Authorization: Bearer <accessToken>`

## 1. Модель хранения

Вместо одного токена — список аккаунтов:

```ts
type Account = {
  userId: string;
  userName: string;
  fullName?: string;
  avatar?: string | null;
  isVerified?: boolean;
  accessToken: string;
  refreshToken: string;
  expiresAt: number; // timestamp, для проактивного refresh
};

type AuthState = {
  accounts: Account[];
  activeUserId: string | null;
};
```

Персистить в хранилище, которое **уже используется в проекте** (тем же способом, что и сейчас). Ключ хранит JSON-объект, а не строку токена.

## 2. Логин — добавляет, а не затирает

- После успешного `/Account/login` подтянуть профиль (`/UserProfile/get-my-profile`), собрать `Account`, **добавить в массив**.
- Если `userId` уже есть в списке — обновить его токены и профиль (не создавать дубликат).
- Сделать активным только что вошедший аккаунт.
- Экран «Добавить аккаунт» = тот же логин, но **не очищает** существующий список.

## 3. HTTP-клиент — токен активного аккаунта

- Подставлять в `Authorization` токен **активного** аккаунта, а не глобальную переменную.
- Если используется `axios` — переписать request-интерцептор; если `fetch`-обёртка — точку, где ставится заголовок.

## 4. Refresh — по аккаунту, а не «текущему»

**Критично:** при 401 обновлять токены **того аккаунта, чей запрос упал**, а не активного (запрос мог уйти от фонового аккаунта).

- Response-интерцептор ловит 401 → берёт `refreshToken` **этого** аккаунта → `POST /Account/refresh-token` → обновляет пару в списке → повторяет исходный запрос.
- **Очередь / дедупликация:** если несколько запросов упали с 401 одновременно — делать **один** refresh, остальные ждут его результата. Иначе ротация убьёт токен: второй refresh придёт со старым значением, бэкенд посчитает это компрометацией и **отзовёт все сессии**.
- Реализовать это **на каждый аккаунт отдельно** (map: `userId → Promise<refresh>`).
- Если refresh упал (401/невалиден) → удалить этот аккаунт из списка; если он был активным → переключиться на следующий или увести на логин.
- Опционально: проактивный refresh по `expiresAt` до истечения.

## 5. Переключение аккаунта

```ts
switchAccount(userId: string): void
```

- Меняет `activeUserId`.
- **Обязательно очищает клиентский кэш и стейт** предыдущего аккаунта: лента, профиль, чаты, счётчики, любые закэшированные ответы. Если используется `react-query` / RTK Query — сбросить кэш (`queryClient.clear()` / `dispatch(api.util.resetApiState())`). Иначе покажутся данные прошлого аккаунта.
- **Переподключить real-time (SignalR)**: разорвать соединения хабов (Notification / Chat / Presence / Live) и переподключить с новым токеном.
- Перезагрузить данные текущего экрана; при необходимости — редирект на главную.
- Переключение должно ощущаться мгновенным (без промежуточного экрана логина).

## 6. Выход

- `logout(userId)` — вызвать `POST /Account/logout` токеном **этого** аккаунта, убрать его из списка.
- Если вышли из активного → переключиться на следующий в списке; если список пуст → на экран логина.
- Добавить «Выйти из всех аккаунтов».

## 7. UI

- Переключатель аккаунтов (шторка / дропдаун по клику на аватар или в настройках): список аккаунтов с аватаром, `@username`, галочкой верификации, отметкой активного.
- Кнопка «Добавить аккаунт» → логин без потери списка.
- Действие «Выйти» на каждом аккаунте.
- Лимит: **до 5 аккаунтов** (как в Instagram).

## 8. Next.js-специфика

- Если есть middleware/guard, читающий токен из cookies — научить его читать активный аккаунт из новой структуры.
- Если есть SSR/RSC-запросы с токеном — использовать токен активного аккаунта; учесть, что список аккаунтов может жить только на клиенте (тогда защищённые данные грузить на клиенте либо синхронизировать активный токен в cookie).
- **Не хранить токены в глобальных переменных модуля** — они шарятся между запросами на сервере.

## Требования к качеству

1. Не ломать текущий флоу логина/логаута для пользователей с одним аккаунтом.
2. Строгая типизация (TypeScript), если проект на TS.
3. Никаких гонок при refresh (см. §4) — иначе ротация токенов отзовёт все сессии.
4. При переключении не должно «протекать» ни одного байта данных прошлого аккаунта.
5. Гварды приватных роутов работают с активным аккаунтом.
6. Обработка edge-кейсов: refresh упал; аккаунт удалён/забанен на сервере; переключение во время незавершённых запросов (отменять их); синхронизация между вкладками через `storage`-событие (опционально).
7. Токены не логировать.

## Зависимость от бэкенда

Мультиаккаунт работает и на текущем бэкенде, но **комфортно** — только с refresh-токенами (§14 ТЗ-расширения: «Активные сеансы + Refresh-токены»). Без них access-токен протухает и при переключении будет требовать повторный вход. Убедись, что бэкенд отдаёт пару `accessToken` + `refreshToken` и имеет `POST /Account/refresh-token`.
